# AI and code review — 2026-10-08

Scope: AI `4782c65` (`kb/batch1`), contrasted with core `9563626` and preview
`1c077ae`; static inspection of testbed `0665818`. See
[overview](PROJECT_OVERVIEW.md) for locations. Findings concern inspected paths,
not a claim that every line or all experimental branches were audited.

## Judgment

The project has a credible engine/observation/knowledge foundation and a meaningful
heuristic prototype. The crate boundaries and correctness tests are its strongest
parts. The next gains should come from aligning decisions with beliefs, fixing
state/configuration contracts, and making evaluation reproducible. Expanding
search or adding learning first would make existing uncertainty harder to diagnose.

## Findings

### F1 — Corrected: an unused pass reader obscured missing pass-choice inference

The original review overstated the runtime impact. Following all call sites during
the first implementation iteration found that `PassReading::of` and `likelihood`
had **no active inference caller**. Comments claiming the old reader was in use
were stale. `Mind::signals` applies bid evidence; its feature posterior and card
table account for exchange constraints without evaluating the giver's pass choice.

C42 selects passes with fitted feature weights. The older HP/HK scorer and its
reader were dormant competing implementations, not a live disagreement between
selection and inference. They have now been removed, including their unused
configuration and tests. The active feature calculations and trump-plan helper
remain in the policy layer, with frozen choices/explanations checked before/after.
See the [exchange checkpoint](checkpoints/2026-10-08-exchange-cleanup.md).

Pass-choice interpretation is still missing capability. A future reader needs
the same choice semantics evaluated from the hypothetical giver's information,
not the recipient's private cards. Do not add a `beliefs -> heuristic` dependency;
extract a shared lower-level owner when a real second consumer exists. See
[passing models](PASSING.md) for the distinction and the remaining decisions.

### F2 — High: the inspected fit reports cannot demonstrate generalisation or strength

`crates/heuristic/src/passing/features.rs` describes conditional-logit fitted weights;
`crates/heuristic/src/bidding.rs:115` describes fitted take-140 log odds.
The referenced outer-workspace scripts `tools/kbstudy/passfit.py` and `quietfit.py`
fit on all loaded rows and then report accuracy on those same rows. No held-out
evaluation is present in those scripts. Their source data and fitting procedure
are also outside this AI checkout.

This is an interpretable, empirically fitted policy, even where comments say
"Not tuned". Later comments record owner requests to try these models; this review
does not treat earlier no-learning wording as proof of an unauthorised change.
Label the evidence accurately and preserve its lineage. Use game/session-separated
evaluation; distinguish human agreement from duplicate-deal score and concrete
strategic mistakes. Do not impose a new numerical agreement target on owner review.

### F3 — Medium, reproduced: reusing an agent across histories can retain stale facts

`crates/heuristic/src/lib.rs:198` identifies a continuing view by seat, initial
hand, seat kinds, event count, and just the last previously applied event.
It does not verify the earlier prefix or a game/history identity.

Reproduction uses two legal auctions on deal seed 42: S0 bids 120 versus 125,
then S1 passes in both. Reuse one agent for S2's views. Its second `Mind` still
reports 120; a fresh agent reports 125. Both views have the same last event and
length. This affects the public reuse contract and future replay/branch caching.
The current testbed creates fresh agents per decision, limiting its present exposure.

Give views a history identity/revision with a sound extension contract, or validate
the prefix before incremental reuse. Changing public belief parameters must also
invalidate the cached `Mind`; parameters are currently public and absent from this key.

### F4 — Medium, reproduced: parameter parsing does not validate values

`crates/heuristic/src/params.rs:121` and the convention parameter setter check
parsing only. `Params::from_toml("trust_partner = NaN")` succeeds. Values outside
probability ranges and very large solver workloads are likewise not bounded by
a semantic validation step. The testbed accepts this text through `SeatCtl::params`.

Validate finite numbers, probability ranges, temperature semantics, and supported
solver limits at construction/configuration boundaries. Preserve deliberate zero
settings such as disabling the endgame. Return typed errors before inference.

### F5 — Medium: sequential evidence is described more strongly than implemented

`crates/eval/src/stats.rs:34` describes an anytime-valid confidence sequence, but
also says the implementation substitutes sample variance and is approximate.
`crates/eval/src/duplicate.rs:231` always builds its headline verdict from a fixed
normal interval, including after sequential stopping; the sequential result appears
later in the report. These are different evidence claims.

For initial qualification use a predeclared fixed sample size and label the normal
interval as approximate. If sequential stopping is retained, use a justified bound
and make the headline use that same rule. Add edge cases for small/constant samples
and invalid configuration. The cited [Howard et al. paper](https://arxiv.org/abs/1810.08240)
develops guarantees under specified conditions; citing it alone does not establish
those conditions for this implementation.

### F6 — Medium: branch and environment divergence obscures what is actually runnable

Core `main`, the squashed preview, and newer local policy commits are different
states. The local branch inherits an old README/architecture draft and a two-line
`.gitignore`; preview contains stronger private-data exclusions and an environment
variable for player grouping. Reconcile these before publication; do not blindly
publish the local branch's history.

The testbed manifest has sibling path dependencies, while the sibling AI currently
has only core crates. `cargo metadata --offline --locked --no-deps` fails because
`MarjapussiAI/crates/agent/Cargo.toml` is missing there. This is a checkout-pairing
issue, not evidence that the server source is intrinsically unbuildable. Record
both repository revisions and create a dedicated runnable sibling pair.

### F7 — Medium: the local server serialises long work under its store lock

Testbed `crates/server/src/lib.rs:33` uses one `Arc<Mutex<Store>>`.
`api::auto` and `api::run` hold it while replaying and deciding; `batches` uses
`spawn_blocking` but still holds the same store lock over the batch. `game::decide`
creates a fresh agent each move, rebuilding its inference state.

This is workable for a small local debugging tool, but is a clear responsiveness
and multi-game limit. Move CPU work away from async request execution and long
store-lock sections, then persist with the existing step/conflict checks. Reuse
agent state only after F3 is fixed. No server throughput benchmark was run.

## AI-method qualifications

- The exact facts/convention-beliefs distinction is appropriate. Hidden-hand-swap
  tests are meaningful evidence; they are not a mathematical proof of all fairness properties.
- `solver::evaluate` solves separate possible deals and aggregates the answers.
  Its `exact` field means all consistent deals were enumerated, not that one
  information-consistent strategy was solved optimally. The implementation calls
  itself PIMC. Keep it as a candidate aid and measure it against the heuristic.
  [Long et al.](https://ojs.aaai.org/index.php/AAAI/article/view/7562) explain why
  PIMC can work well despite its theoretical limitations; that is not a guarantee for this agent.
- Joint probabilities such as team pairs and void/ruff combinations use products
  of marginals in places (`beliefs/src/reads.rs`, `table.rs`). Fact consistency
  alone does not establish probability calibration. Compare approximation error
  against exact small-deal enumeration before increasing model complexity.
- Raising is explicitly off (`heuristic/src/lib.rs:275`); coordinated planning is
  unfinished. Describe these as remaining capability work, not accidental regressions.

## Code quality

Keep the nine-crate split, typed domain state, facade exports, deterministic
evaluation, and independent engine/solver comparisons. There is no case here for
a wholesale rewrite. Most production modules are reasonably bounded; the largest
are the knowledge sampler (~684 lines), knowledge facade (~633), and belief feature
DP (~626). The 824-line belief-study binary is a tooling maintenance issue.

Concentrate refactoring on concrete ownership problems: obsolete policy readers,
parameter/provenance ownership, history identity, and server work scheduling.
Remove unused legacy paths only after checking study users. The exchange cleanup
removed obsolete passing tests and redundant argmax reconstructions, retained
independent scenarios, and added a comparison with frozen pre-cleanup decisions.

No CI workflow or pinned Rust toolchain/MSRV was found in the reviewed AI tree.
The tested local toolchain is Rust/Cargo 1.91.1. Two semantic tests are ignored:
the owner card-choice case at `heuristic/tests/play.rs:88` and pass-read calibration
at `tools/tests/selfplay.rs:89`. Resolve or explicitly track them separately from
deliberately ignored performance experiments.
